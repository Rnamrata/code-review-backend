Service dependency map
======================
Status: matches the code on master (updated for the LLM adapter, the rule cards,
the secret scan, PMD, the "why" cards, request validation, readiness, logging and metrics).
Replaces the v1 map (sessions, parser, RAG communicator, report generator),
which is still on branch archive/v1-node-primary.

Request flow
------------
Before a request reaches the controller (src/app.ts): helmet, CORS, metrics, access log,
request id and the body parser. On /review it also passes the rate limiter
(routes/index.ts) and request validation (middlewares/validateReview.middleware.ts,
schemas/review.schema.ts). /health, /ready and /metrics are answered in app.ts.

What each adapter depends on
----------------------------
eslint.adapter   eslint, @eslint/js, typescript-eslint, eslint-plugin-security
                 (all in-process; nothing external to install)
ruff.adapter     node child_process + the external "ruff" binary (RUFF_BIN)
pmd.adapter      node child_process + the external "pmd" launcher (PMD_BIN), which needs
                 Java; the code goes into a private temp folder removed after each run
secrets.adapter  nothing external: patterns for provider keys and secret-looking names
llm.adapter      HTTP call to Ollama (/api/chat), only when LLM_ENABLED=true
                 javaRules.ts, pythonRules.ts and scriptRules.ts (through ruleCards.ts)
                 pick the reminders for the prompt
why/             whyCards.ts (the cards) and whyMatcher.ts (which finding gets which),
                 used by the orchestrator after merging

Shared by everything
--------------------
models/finding.ts       Finding, Severity, FindingSource, SEVERITY_ORDER
models/review.model.ts  ReviewRequest, ReviewResponse, ReviewWarning,
                        ReviewSummary, Analyzer
config/app.config.ts    environment settings
utils/logger.util.ts    winston logger
services/metrics.service.ts  counters behind GET /metrics, recorded by the
                        orchestrator and the middlewares
services/readiness.service.ts  GET /ready: Ruff, PMD and (when on) Ollama

Dependency rules
----------------
- models import nothing from the rest of the project.
- adapters import models, config, constants and utils (and their own helper
  files, such as javaRules.ts). They never import the orchestrator, the merger
  or each other.
- the orchestrator is the only place that knows which adapters exist.
- the merger and the summary builder are pure functions over Finding[].
  No I/O, no logging, so they are the easiest things to unit test.
- controllers talk to the orchestrator, never to an adapter directly.

Build order (bottom-up)
-----------------------
1. models
2. config, constants
3. utils (logger, validator, response formatter)
4. adapters (independent of each other, can be built in any order)
5. findingsMerger, reviewSummary
6. reviewOrchestrator
7. controller, routes
8. server.ts

External requirements
---------------------
- Node >= 20.19
- ruff on PATH, or RUFF_BIN set (Python analysis is skipped with a warning
  if it is missing)
- PMD with Java, or PMD_BIN set (Java analysis is skipped with a warning if it
  is missing; PMD_ENABLED=false turns it off). The Docker image includes both
- Ollama with a coding model such as qwen2.5-coder:7b (optional, LLM_ENABLED=true;
  without it every language gets its linter and the secret scan only)

Not part of this service any more
---------------------------------
Sessions, file upload, JSON persistence, chat history, the RAG communicator,
the report generator and the hand-written analyzers. The chatbot owns the
conversation; this service only turns code into findings.

Why keep this map
-----------------
- Shows where a new analyzer plugs in (one file plus one registration line).
- Keeps adapters independent so one can fail without touching the others.
- Guides the test plan: pure functions first, then adapters, then the route.
